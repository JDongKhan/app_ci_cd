1. 背景与目标

ShipFlow 是一套内部研发交付平台，把「应用 → 需求 → 任务 → CI 流水 → 合并 → 打包 → 产物」串成一条可追踪的流水线。

一期要解决：

  • 开发、测试、管理员、产品按账号区分角色，按角色执行各自动作
  • 应用配置与需求解耦，需求不绑应用，新建流水时再选应用
  • 一个任务可以挂多条 CI 流水，例如同一任务同时打 Android APK 与 iOS IPA
  • 每条流水独立完成 QA、UAT、Release、master 四个阶段的合并与打包
  • 任务状态由任务详情页的按钮推进，流水只负责合并、冲突、打包、通过和拒绝
  • 打包机单机单 clone，构建串行执行，日志和产物随时可查

一期不做：Jenkins 接入、审批流、镜像构建、蓝绿发布、自动回滚、多构建机、SSO。

2. 一期范围

2.1 功能范围

  • 账号与角色：开发、测试、管理员、产品；除管理员外分 L1~L3
  • 权限：菜单权限按角色 × 级别配置；操作动作按角色执行
  • 应用配置：平台、仓库、分支映射、构建脚本、产物类型、产物路径
  • 需求：编号、标题、描述、开发 / 测试 / 产品负责人、测试人员、优先级、开始 / 结束时间
  • 任务：负责人、计划时间、任务状态、多条 CI 流水
  • 流水：Feature 分支、四阶段合并、冲突处理、合并记录、构建记录、产物
  • 打包：单机队列、实时进度、失败原因、完整日志
  • 产物：成功产物下载；正在打包和失败的构建也在产物页可见

2.2 三类状态

对象 状态来源 说明
需求 由任务聚合 待拆任务 / 待开始 / 进行中 / 有超时 / 已完成
任务 任务详情按钮推进 未开始 / 开发中 / 已提测 / 测试中 / 待发布 / 已结束；超时按时间和状态派生
流水 合并与打包动作推进 未开始 / 合并中 / 冲突 / 已合入 / 包就绪 / 自测通过 / 测试中 / 验证中 / 已验证 / 已合入 master

任务状态和流水状态解耦。流水动作会校验任务状态：任务未「开始开发」不能合并 QA；未「开始测试」不能合并 UAT；未「进入待发布」不能合并 Release。

3. 技术选型

层 选型 说明
前端 Vue 3 + TypeScript + Vite + Element Plus + Pinia + Vue Router + TanStack Query 权限后台、表格和表单密集；用 Element Plus 变量覆盖成原型蓝色风格
后端 NestJS + class-validator + JWT + bcrypt + Swagger 模块化清晰，TypeScript 全栈
ORM Prisma 一期 SQLite，后续切 PostgreSQL 时查询层改动小
数据库 SQLite 文件 data/shipflow.db 不需要安装数据库服务，随项目生成
构建队列 内存 FIFO + 单消费者 一期单构建机；队列不持久化，重启后需重新触发
进程执行 execa + git CLI 直接调用本机 git，行为与研发本地一致
产物匹配 fast-glob 按应用配置的 artifactPattern 匹配产物
日志 文件 + HTTP 轮询增量 需求要求运行中可轮询；GET /api/builds/:id/log?offset=
产物存储 本地 storage/ 后续可替换为 MinIO/S3
工程 pnpm workspace web、api、worker 与 shared 包统一管理

4. 总体架构

flowchart TB Web["Vue 3 + Element Plus"] --> API["NestJS API"] API --> DB[("SQLite<br/>data/shipflow.db")] API --> Queue["内存构建队列<br/>FIFO + 单消费者"] Queue --> Runner["BuildRunner<br/>子进程"] Runner --> Git[("Git 仓库")] Runner --> Artifact[("storage/artifacts")] Runner --> Log[("storage/logs")] Web -.->|轮询构建日志| API

架构原则：

  1. 控制面与执行面分离：API 负责账号、权限、需求、任务、流水状态和门禁；构建执行放在子进程。
  2. 任务状态与流水状态解耦：任务按钮推进任务状态，流水只管合并、冲突和打包。
  3. 状态机服务端权威：前端按钮只做展示，所有状态流转和门禁在 API 层再次校验。
  4. 单机串行：一期只有一个构建机，打包必须排队，构建期间禁止切分支合并。
  5. 存储可迁移：业务代码依赖仓储接口，不直接依赖 SQLite 或 Prisma。

5. 本地运行形态

pnpm install
pnpm db:init     # 生成 data/shipflow.db 并写入种子数据
pnpm dev         # 同时启动 web 与 api
  • Web：http://localhost:5173
  • API：http://localhost:3000
  • 构建子进程由 API 在同一台机器上拉起
  • 不需要安装 PostgreSQL、Redis、Jenkins

目录约定：

data/shipflow.db                         # 运行时数据库，git 忽略
prisma/schema.prisma                     # 模型定义
prisma/migrations/**/migration.sql       # 建表 SQL
prisma/init.sql                          # 演示用合并版初始化 SQL
storage/artifacts/<appId>/<buildId>/     # 成功产物
storage/logs/<appId>/<buildId>.log       # 构建日志
storage/tmp/                             # 产物中转
workspace/<appId>/                       # git clone，可重建

5.1 关于 .sql 与 .db

SQLite 的运行时文件是 .db 或 .sqlite，.sql 只是建表和种子脚本。

  • 源码交付：提交 prisma/migrations/**/migration.sql 和 prisma/init.sql，首次运行 pnpm db:init 生成 data/shipflow.db
  • 演示打包：构建时生成带种子数据的 data/shipflow.db，随演示包分发
  • 运行中的 .db 不提交 git

6. 数据存储

6.1 存储分层

层 存什么 是否事实来源
SQLite 账号、权限、需求、任务、流水、合并、冲突、构建、产物元数据、事件 是
本地文件 git clone、成功产物、完整构建日志 产物和日志是；clone 可重建
内存 构建队列、当前构建进程、串行锁 否

6.2 表清单

表 作用
users 账号、角色、级别
role_permissions 角色 × 级别权限矩阵；权限项定义在前端配置
apps 应用、仓库、分支、构建脚本、产物配置
requirements / requirement_qa_members 需求、三个负责人、测试人员
tasks 任务、负责人、计划时间、任务状态
pipelines CI 流水、Feature 分支、流水状态、rework 信息
pipeline_merges 合并记录，作废只打标记
pipeline_conflicts / pipeline_conflict_files 冲突记录与冲突文件
pipeline_events 流水事件与审计
builds 构建记录、进度、失败原因、日志路径
artifacts 成功产物元数据

6.3 关键约束

  1. 任务状态落库。tasks.status 取 none|dev|ready|testing|release|done，由任务详情按钮修改；超时由 due_at + status 派生。
  2. 流水不再有 ready_test。提测是任务状态，流水 dev_passed 只表示「自测通过」，等任务进入测试中后才能合并 UAT。
  3. 构建状态只有 running|success|failed。构建记录在真正开始执行时创建；排队在内存队列里，不写 builds。
  4. 产物页按构建展示。GET /api/artifacts 返回构建列表，包含成功、打包中、失败三种；成功构建才有产物。
  5. 下载不鉴权。按需求产物下载直链不鉴权；artifact_download 权限项保留，但一期不参与下载校验。
  6. 日志随时可查。完整日志落文件，builds.log_tail 保留最后 200 行；运行中通过 /log?offset= 轮询增量。
  7. 合并记录不删除。自测拒绝、测试不通过、验证不通过时用 invalidated_at 标记作废，保留审计。
  8. 提交记录按任务一份。一个任务共用一条 Feature 分支和一个仓库，多条流水只是产物不同。

6.4 文件布局

storage/
├─ artifacts/<appId>/<buildId>/<file>     # 成功产物，长期保留
├─ logs/<appId>/<buildId>.log            # 完整构建日志
└─ tmp/<buildId>/                        # 产物中转

workspace/<appId>/                       # git clone，可重建

6.5 迁移到 PostgreSQL

需要改：

项目 改动

  • 仓储接口签名

7. 核心流程

7.1 任务状态推进

当前 按钮 谁点 进入条件
未开始 开始开发 开发 无
开发中 提测 开发 至少一条流水「自测通过」且有成功的 QA 包
已提测 开始测试 测试 至少一条流水「自测通过」
测试中 进入待发布 测试 至少一条流水有成功的 UAT 包
待发布 完成发布 · 已结束 测试 至少一条流水 Release 验证通过并合回 master

超时：

  • 未开始 / 开发中超过结束时间 → 开发超时
  • 已提测 / 测试中 / 待发布超过结束时间 → 测试超时
  • 已结束优先级最高，不再显示超时

7.2 流水合并与打包

流水状态：

  • none → 合并 QA → dev_merged / dev_conflict
  • dev_merged → 打包 QA → dev_built
  • dev_built → 自测通过 → dev_passed；拒绝 → dev_merged
  • dev_passed →（任务进入测试中）→ 合并 UAT → testing / test_conflict
  • testing → 打包 UAT；有 UAT 包后可合并 Release
  • testing → 合并 Release → release_check / release_conflict
  • release_check → 打包 Release → 验证通过 → release_verified
  • release_verified → 合回 master → done

任务状态校验：

  • 任务不是开发中，合并 QA 置灰
  • 任务不是测试中，合并 UAT 置灰
  • 任务不是待发布，合并 Release 置灰

三处硬门禁：

  1. 提测前必须有 QA 包并自测通过，且包对应最新一次 QA 合并
  2. 合并 Release 前必须有成功的 UAT 包
  3. 合回 master 前必须有成功的 Release 包并验证通过

7.3 冲突处理

  • 冲突时流水停在当前阶段，弹出冲突通知
  • 「冲突分支」是任务里配置的 Feature 分支，不是临时分支
  • 系统基于 Feature 分支创建临时分支：temp/Conflict_<目标分支>_feature/<feature>_<yy.MMDD.HHmm.ss>
  • 开发在临时分支解决冲突并推送后，回到平台点「已解决冲突 · 合并」
  • 平台把临时分支合入目标分支，Feature 分支不做改动
  • 冲突态流水只有「已解决冲突 · 合并」一个按钮

7.4 构建队列与日志

  • 打包必须排队，合并不排队
  • 单机单 clone，构建期间任何流水禁止切分支合并
  • 运行中的流水禁止再次点打包
  • 构建状态：running|success|failed
  • 运行中展示进度；失败记录 failReason，产物为空
  • 流水卡片有「打包日志」按钮，运行中和失败都能看
  • 完整日志落文件；运行中通过 GET /api/builds/:id/log?offset= 轮询增量
  • 产物页同时展示已入库、打包中、失败三种构建

7.5 打包产物

  • 成功构建生成产物，记录名称、类型、大小、SHA256、路径
  • 产物不可变，重新打包生成新的构建和产物
  • 失败构建不生成产物，但构建记录和日志保留
  • 产物下载直链不鉴权，按需求可直接分享
  • 产物页支持按应用筛选，展示状态、进度、失败原因

8. 权限设计

  • 菜单权限按「角色 × 级别」配置，决定左侧菜单和页面可见性
  • 操作动作按角色决定：开发、测试、管理员、产品
  • 管理员固定拥有全部菜单和动作，不参与矩阵编辑
  • 权限项定义放在前端 apps/web/src/config/permissions.ts，当前 5 组 23 项（原型 v2 新增 req_member）；角色权限矩阵入库
  • 权限矩阵支持按权限为行、角色 × 级别为列勾选，管理员列只读全选
  • req_member 控制维护需求测试人员
  • 操作类权限项保留在配置中，一期动作校验以角色 + 状态为准

10. 前端设计

  • /login：原型阶段选账号进入；正式环境改为账号 + 密码 + JWT
  • /home：三个 tab：进行中 / 跟我有关 · 其他状态 / 我的需求
  • /board：七列任务看板，只展示状态
  • /reqs、/reqs/:id：需求列表与详情，含测试人员
  • /apps：应用配置
  • /artifacts：产物 / 构建列表，含打包中与失败
  • /roles、/staff：仅管理员
  • /spec：需求说明
  • 任务详情：状态推进按钮 + 概览 / CI 流水 / 提交记录 / 构建记录

构建日志使用轮询，不引入 SSE。

12. 风险与注意事项

  1. SQLite 单写者：开启 WAL 与 busy_timeout，一期保持单进程写入。
  2. 构建机工具链：iOS 依赖 macOS + Xcode，Android 依赖 SDK；构建失败要有明确日志。
  3. Git 凭据：使用本机 SSH agent 或 deploy key，不把私钥写库。
  4. 构建脚本可信输入：buildScript 等同于执行任意命令，只有管理员能改应用配置。
  5. 下载不鉴权：按需求产物直链不鉴权；内部演示可接受，正式环境建议改为限时签名链接。
  6. 日志增长：单次日志按 50MB 截断，历史日志按保留天数清理，保留 log_tail。
  7. 路径安全：产物读取、日志读取必须做路径规范化和越界校验。
  8. 队列不持久化：一期内存队列，进程重启后排队任务丢失，需要用户重新触发打包。

14. 关键决策记录

决策 选择 原因
任务状态 落库，由任务按钮推进 需求说明明确任务状态与流水解耦
流水职责 只做合并、冲突、打包、通过 / 拒绝 开始开发、提测、开始测试、待发布、结束都在任务上
构建状态 running / success / failed 与需求说明和原型一致；排队放内存
