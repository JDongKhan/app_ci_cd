1. 文档说明

本文说明一期各模块的具体设计：

  • 账号、角色、级别与权限
  • 应用、需求、任务
  • 任务状态机与任务级门禁
  • 流水状态机、合并、冲突、rework
  • 构建队列、进度、失败原因、日志
  • 打包产物与产物页
  • 表结构、接口、页面和测试要点

2. 设计原则

  1. 任务状态与流水状态解耦。任务状态由任务详情按钮推进；流水只负责合并、冲突、打包、通过 / 拒绝。
  2. 状态机服务端权威。前端按钮只做展示，所有状态流转和门禁在 API 层校验。
  3. 任务状态落库。tasks.status 是任务自己的字段，不由流水实时推导。
  4. 产物不可变。一次构建对应一批产物，重新打包生成新的构建和产物。
  5. 文件与元数据分离。大文件、日志落磁盘，数据库只存路径、大小、哈希和状态。
  6. 存储可迁移。业务代码依赖仓储接口，不直接依赖 SQLite 或 Prisma。

3. 模块与数据关系

User 1 ── N Requirement（测试人员）
User 1 ── N Task（开发负责人）

4. 通用约定

约定 说明
主键 TEXT，应用生成 UUID
时间 UTC，领域层用 Date，SQLite 存 DATETIME
状态 TEXT + TypeScript 联合类型
JSON TEXT，仓储层序列化；切 PostgreSQL 后可升级 jsonb
布尔 ORM 映射，业务代码不直接写 0/1

5. 账号与角色

5.1 角色

角色 标识 说明 级别
开发 dev 开始开发、提测、合并 QA、打包 QA、自测 L1 / L2 / L3
测试 qa 开始测试、进入待发布、完成发布、合并 UAT / Release / master、打包、验证 L1 / L2 / L3
产品 pm 提需求、维护需求、看进度，不操作代码与打包 L1 / L2 / L3
管理员 admin 全部菜单和动作，维护应用、权限、人员 无级别

5.2 users 表

字段 类型 说明
id TEXT 主键
account TEXT 登录账号，唯一，小写
password_hash TEXT bcrypt 哈希
name TEXT 显示名
role TEXT dev / qa / admin / pm
level TEXT l1 / l2 / l3；admin 为 NULL
team TEXT 团队
active INTEGER 1 启用，0 停用
last_login_at DATETIME 最近登录
created_at DATETIME 创建时间
updated_at DATETIME 更新时间

5.3 登录

  • 原型为演示方便，登录页直接选账号进入
  • 正式实现使用账号 + 密码 + JWT，账号数据模型不变
  • 账号必须 active = 1
  • 登录成功更新 last_login_at
  • 登录失败统一提示，不区分账号不存在或密码错误
  • JWT 载荷包含 sub、role、level，有效期 7 天

5.4 人员管理

仅管理员：

  • 新增账号：账号、姓名、初始密码、角色、级别、团队
  • 编辑账号：姓名、角色、级别、团队、启用状态
  • 重置密码
  • 停用账号：active = 0

约束：

  • 账号创建后不可修改
  • 管理员不能停用自己
  • 至少保留一个启用状态的管理员
  • admin 的 level 必须为空

6. 权限设计

6.1 权限分类

类型 说明 示例
菜单权限 控制左侧菜单和页面可见性 home、board、reqs
操作权限 权限配置中的动作项 merge_qa、verify、req_member
管理员专属 只有 admin 可用 roles、staff

需求说明明确：级别只决定菜单可见范围，具体可执行动作仍由角色决定。因此：

  • 菜单导航由「角色 × 级别」矩阵决定
  • 流水和任务动作由角色 + 当前状态决定
  • 操作权限项保留在配置中，用于说明和后续细化，一期不作为最终动作门禁

6.2 表结构

表 关键字段 说明
role_permissions role、level、permission_key 角色 × 级别矩阵；权限项定义在前端

权限项定义放在前端 apps/web/src/config/permissions.ts，当前 5 组 23 项。前端负责渲染权限分组和矩阵，提交选中的权限 key；后端只存储 (role, level, permission_key)，不维护权限目录表。新增权限项时改前端配置即可，不需要迁移数据库。

6.6 权限管理

  • 只有 admin 可以访问 /api/roles/perms
  • 矩阵按「权限为行、角色 × 级别为列」
  • 管理员列只读全选
  • 列头支持全选 / 清空
  • 保存时校验权限 key、角色、级别
  • 支持导入 JSON，结构同原型 perm-config
  • 权限变更后重新拉取 /api/me

8.1 requirements 表

title TEXT 标题

8.2 requirement_qa_members 表

字段 类型 说明
requirement_id TEXT 需求
user_id TEXT 测试人员

复合主键 (requirement_id, user_id)。测试负责人自动包含在测试人员内；req_member 权限可维护该列表。

8.3 负责人规则

  • 开发负责人 role = dev 且启用
  • 测试负责人 role = qa 且启用
  • 产品负责人 role = pm 且启用
  • 测试人员必须 role = qa 且启用
  • 新建任务时，任务负责人默认取需求的开发负责人

8.4 需求状态

需求状态只读，由任务聚合：

状态 条件
待拆任务 还没有任务
待开始 全部任务都是未开始
进行中 至少一个任务在开发中 / 已提测 / 测试中 / 待发布
有超时 至少一个任务超时，且不是全部结束
已完成 全部任务已结束

优先级：已完成 > 有超时 > 进行中 > 待开始 > 待拆任务。

8.5 「我的需求」

  • 开发：dev_owner_id = 当前用户
  • 测试：qa_owner_id = 当前用户 或在 requirement_qa_members
  • 产品：pm_owner_id = 当前用户
  • 管理员：全部

9.1 tasks 表

字段 类型 说明

updated_at DATETIME 更新时间

9.2 任务状态

状态 标识 推进按钮 谁点 进入条件
未开始 none 开始开发 开发 无
开发中 dev 提测 开发 至少一条流水 dev_passed 且有成功 QA 包
已提测 ready 开始测试 测试 至少一条流水 dev_passed
测试中 testing 进入待发布 测试 至少一条流水有成功 UAT 包
待发布 release 完成发布 · 已结束 测试 至少一条流水 done 或 release_verified
已结束 done — — 不再推进

任务状态是任务自己的字段，不由流水实时推导。

9.3 超时

判定 条件
开发超时 超过结束时间，且状态为未开始 / 开发中
测试超时 超过结束时间，且状态为已提测 / 测试中 / 待发布
已结束 状态为 done，优先级最高，不显示超时

展示上区分开发超时和测试超时；看板「超时」列用不同 pill，首页 KPI 显示「开发超时 X · 测试超时 Y」。

9.4 任务进度

任务进度 = 所有流水已完成合并阶段数的平均值 / 4

只统计有效合并，四舍五入为 0~100。

9.5 首页 tab

原型 v8 有三个 tab：

tab 开发 测试 产品 / 管理员
进行中 未开始 + 开发中 已提测 + 测试中 + 待发布 全部未结束任务
跟我有关 · 其他状态 其余任务 其余任务 其余任务
我的需求 开发负责的需求 测试负责或测试人员的需求 产品负责的需求；管理员全部

任务列表不显示负责人，只显示开始 - 结束时间；行尾提供「任务详情」「+ CI 流水」。

9.6 提交记录

  • 一个任务对应一个仓库和一条 Feature 分支
  • 多条流水共用该分支，只是产物类型不同
  • 分支取该任务第一条流水的 branch，仓库取对应应用的 repo
  • 新建流水时校验：同一任务下所有流水必须使用相同仓库和相同 Feature 分支
  • GET /api/tasks/:id/commits?limit=20 通过 git log 读取最近提交，不落库

9.7 任务详情

按钮：

  • 当前状态推进按钮（开始开发 / 提测 / 开始测试 / 进入待发布 / 完成发布）
    • CI 流水
  • 打开需求
  • 删除任务（仅管理员）

tabs：概览 / CI 流水 / 提交记录 / 构建记录。

删除任务为软删除；有正在运行构建时拒绝删除；历史流水、构建和产物保留。

10.3 流水动作与任务状态校验

10.5 冲突处理

pipeline_conflicts：

字段 类型 说明
id TEXT 主键
pipeline_id TEXT 流水
stage TEXT 阶段
temp_branch TEXT 临时分支
created_at DATETIME 创建时间
resolved_at DATETIME 解决时间
resolved_by TEXT 解决人

pipeline_conflict_files：id、conflict_id、path。

冲突通知中的「冲突分支」是任务配置的 Feature 分支，不是临时分支。临时分支命名：

temp/Conflict_<目标分支>_feature/<feature>_<yy.MMDD.HHmm.ss>

例：temp/Conflict_qa_feature/transfer-direct-filter_26.1119.0942.31

处理流程：

  1. 合并失败后 git merge --abort
  2. 基于 Feature 创建临时分支并推送
  3. 写入冲突记录和冲突文件
  4. 流水进入冲突态
  5. 开发在临时分支解决冲突并推送
  6. 平台点「已解决冲突 · 合并」
  7. 平台 fetch 临时分支，合入目标分支
  8. 标记冲突记录已解决，写入合并记录，继续流程

冲突态流水只有「已解决冲突 · 合并」一个按钮。

10.6 退回与 rework

动作 结果 作废合并
自测拒绝 流水回 dev_merged，任务保持开发中 QA 合并
测试不通过 流水回 dev_merged，任务回到开发中 UAT、Release 合并
Release 验证不通过 流水回 testing，任务回到测试中 Release 合并

pipelines.rework_* 保存最近一次退回信息；pipeline_events 保存完整历史。

11. 构建设计

11.1 builds 表

字段 类型 说明
id TEXT 主键
pipeline_id TEXT 流水
stage TEXT 构建阶段
merge_sha TEXT 对应合并提交
status TEXT running / success / failed
progress INTEGER 0~100
started_at DATETIME 开始时间
finished_at DATETIME 结束时间
duration_ms INTEGER 耗时
exit_code INTEGER 退出码
fail_reason TEXT 失败原因

log_size_bytes INTEGER 日志大小

log_truncated INTEGER 是否截断
log_deleted_at DATETIME 日志清理时间
triggered_by TEXT 触发人
created_at DATETIME 创建时间

构建在真正开始执行时插入，状态为 running。排队只在内存队列里，不写 builds。

11.2 队列

  • 内存 FIFO 队列，单消费者，串行执行
  • 打包必须排队；合并不排队
  • 构建期间任何流水禁止切分支合并
  • 运行中的流水禁止再次点打包
  • 进程重启后排队任务丢失，需要重新触发；运行中的构建在启动时标记失败

11.3 执行

  • 工作目录：workspace/<appId>
  • 命令：bash -lc <buildScript>
  • 超时：默认 30 分钟
  • stdout/stderr 按行写入日志文件
  • 进度根据构建步骤或日志行更新
  • 成功：扫描产物、校验、入库，状态 success
  • 失败：记录 fail_reason，状态 failed，产物为空

11.4 日志

  • 路径：storage/logs/<appId>/<buildId>.log
  • 头部写构建上下文：脚本、工作目录、merge sha、触发人、开始时间
  • 每行带时间戳和 [stdout] / [stderr]
  • 结束写退出码、耗时、产物路径
  • builds.log_tail 保存最后 200 行
  • 运行中：GET /api/builds/:id/log?offset=N 返回增量
  • 历史：同一接口 offset 0 返回完整日志
  • 流水卡片有「打包日志」按钮，运行中和失败都能看

11.5 产物页

/artifacts 按构建展示，包含：

  • 已入库：成功构建 + 产物
  • 打包中：运行中构建，显示进度，无产物
  • 失败：失败构建，显示失败原因，无产物

点行打开构建详情，再点「查看打包日志」。

11.6 API

方法 路径 说明
GET /api/artifacts 构建 / 产物列表，含运行中与失败
GET /api/builds/:id 构建详情
GET /api/builds/:id/log 日志，支持 offset 增量

12. 打包产物设计

12.1 artifacts 表

字段 类型 说明
id TEXT 主键
build_id TEXT 所属构建
original_name TEXT 原始文件名
display_name TEXT 平台标准名
type TEXT apk / ipa / jar / war / zip / other
mime_type TEXT Content-Type
size_bytes INTEGER 文件大小
sha256 TEXT 文件哈希
relative_path TEXT 相对 storage/artifacts 的路径
status TEXT available / deleted / missing
download_count INTEGER 下载次数
last_downloaded_at DATETIME 最近下载
created_at DATETIME 入库时间
deleted_at DATETIME 软删除时间

约束：(build_id, relative_path) 唯一。

12.2 命名

<appCode>_<stage>_<yyyyMMdd_HHmmss>_<shortSha>.<ext>
  • shortSha 取该阶段最新有效合并 SHA 前 7 位
  • original_name 保留原始文件名
  • 重名追加 _2、_3
  • 总长度超过 120 字符时截断 appCode

12.3 存储

storage/tmp/<buildId>/                    # 中转
storage/artifacts/<appId>/<buildId>/      # 正式产物
  • 先写临时目录，校验通过后原子移动
  • 同一文件系统用 rename
  • 不允许软链接
  • 可选生成 .sha256

12.4 发现与校验

  • 以 workspace/<appId> 为根目录
  • fast-glob 按 artifactPattern 匹配
  • 不跟随软链接，忽略 .git、node_modules
  • 最多 20 个文件
  • 校验真实路径在工作区内
  • 校验普通文件、大小、扩展名、总大小、磁盘空间

12.5 新鲜度

有效产物需要：

  • artifact.status = available
  • 文件存在
  • 构建 status = success
  • 构建阶段等于目标阶段
  • build.merge_sha 等于该阶段最新有效合并 SHA

过期产物仍可下载，但不能通过门禁。

12.6 下载

GET /api/artifacts/:id/download
  • 按需求不鉴权，可直接分享
  • 校验 relative_path 位于 storage/artifacts 下
  • 文件不存在时标记 missing，返回 410
  • 流式返回，设置 Content-Type、Content-Length、Content-Disposition
  • 异步更新下载次数

安全说明：正式环境建议改为限时签名链接；一期按需求保持不鉴权。

12.7 清理

  • 演示阶段默认全部保留
  • 后续通过 ARTIFACT_RETENTION_DAYS 清理
  • 清理只删文件，记录改为 deleted 并写 deleted_at
  • 启动对账：记录有文件无 → missing；文件有记录无 → 延迟清理

17. 与需求说明的差异说明

以下三处需求说明与当前原型 v8 不完全一致，文档按当前原型执行：

  1. 首页 tab：需求说明写「进行中 / 跟我有关 · 其他状态」两个 tab；原型 v8 增加「我的需求」第三个 tab。本文按三个 tab 设计。
  2. 权限项数量：需求说明写 22 项；原型 v2 perm-config 已增加 req_member，共 23 项。本文按 23 项设计。
  3. 登录方式：原型为选账号模拟登录；正式实现仍使用账号 + 密码 + JWT，账号数据模型不变。

如果这三处以需求说明为准，需要同步调整原型；当前先以原型 v8 为准。

  merge_sha      TEXT NOT NULL,
  status         TEXT NOT NULL DEFAULT 'running',
  progress       INTEGER NOT NULL DEFAULT 0,
  started_at     DATETIME,
  finished_at    DATETIME,
  duration_ms    INTEGER,
  exit_code      INTEGER,
  fail_reason    TEXT,
  log_path       TEXT,
  log_size_bytes INTEGER NOT NULL DEFAULT 0,
  log_tail       TEXT,
  log_truncated  INTEGER NOT NULL DEFAULT 0,
  log_deleted_at DATETIME,
  triggered_by   TEXT REFERENCES users(id),
  created_at     DATETIME NOT NULL
);
CREATE INDEX idx_builds_pipeline_stage ON builds(pipeline_id, stage, created_at);
CREATE INDEX idx_builds_status ON builds(status, created_at);

CREATE TABLE artifacts (
  id                 TEXT PRIMARY KEY,
  build_id           TEXT NOT NULL REFERENCES builds(id),
  original_name      TEXT NOT NULL,
  display_name       TEXT NOT NULL,
  type               TEXT NOT NULL,
  mime_type          TEXT NOT NULL,
  size_bytes         INTEGER NOT NULL,
  sha256             TEXT NOT NULL,
  relative_path      TEXT NOT NULL,
  status             TEXT NOT NULL DEFAULT 'available',
  download_count     INTEGER NOT NULL DEFAULT 0,
  last_downloaded_at DATETIME,
  created_at         DATETIME NOT NULL,
  deleted_at         DATETIME,
  UNIQUE (build_id, relative_path)
);
CREATE INDEX idx_artifacts_build ON artifacts(build_id);
CREATE INDEX idx_artifacts_status_created ON artifacts(status, created_at);
CREATE INDEX idx_artifacts_sha ON artifacts(sha256);
