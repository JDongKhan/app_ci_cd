1. 一期目标与范围

把「应用 → 需求 → 任务 → CI 流水 → 合并 → 打包 → 产物」串成一条可追踪的流水线。一期范围是登录与角色、需求、任务、多条 CI 流水、合并与打包、产物入库。

  • 应用配置与需求解耦：需求不关联应用，应用在新建流水时选择。
  • 一个任务可以挂多条 CI 流水，例如 Flutter 任务同时打 Android APK 与 iOS IPA；产物类型与构建脚本在应用里固定，应用按平台分 Android / iOS。
  • 每条流水独立保存 Feature 分支、目标分支映射、合并记录、构建记录与产物。
  • 提交记录按任务一份：一个任务对应一个代码仓库、一条 Feature 分支，多条流水共用它，只是产出不同产物（apk / ipa / jar 等）。
  • 登录按账号区分角色：开发 / 测试 / 管理员 / 产品；除管理员外每个角色分 L1~L3。
  • 首页只放「我的任务」，列表不提供操作按钮，所有操作都进任务详情；分三个 tab：进行中 / 跟我有关 · 其他状态 / 我的需求。
  • 任务状态由任务详情的按钮推进：开始开发 → 提测 → 开始测试 → 进入待发布 → 完成发布。
  • 流水只负责代码合并与打包：合并、冲突待解决、已解决冲突、打包 QA/UAT/Release、通过、拒绝。
  • 建需求时同时指定开发负责人、测试负责人、产品负责人。
  • 一期不做：Jenkins 接入、审批流、镜像构建、蓝绿发布、自动回滚。

3. 三类状态：需求 / 任务 / 流水

需求管交付范围，任务管人与时间，流水管代码合并与打包。任务状态由任务详情上的按钮推进；流水只负责合并、冲突、打包、通过 / 拒绝。流水没有「开始开发」按钮，一个任务可以有多条流水（Android / iOS）。

3.1 需求状态

由任务聚合，只读，不支持手动改。

状态触发条件说明
待拆任务需求下还没有任务需求刚建，等开发拆任务
待开始有任务，但全部任务都是「未开始」还没有人点开始开发
进行中至少一个任务进入开发中 / 已提测 / 测试中 / 待发布需求在推进中，点需求卡片看各任务状态
有超时任一任务已超时（开发超时或测试超时）只是提示，点进任务看具体是哪种超时
已完成全部任务都已结束（已发布）需求交付完成

3.2 任务状态

任务状态是任务自己的字段，由任务详情的推进按钮修改，共 8 种（含两种超时）。

状态推进按钮谁点进入条件与说明
未开始开始开发开发任务刚建、还没人开始；点「开始开发」后开发才能在该任务的流水上合并 QA
开发中提测开发流水里合并 QA、打包、自测；至少一条流水「自测通过」且有成功的 QA 包才能提测
已提测开始测试测试开发已交付；测试点「开始测试」后任务进入测试中，流水的「合并 UAT」才可用
测试中进入待发布测试流水里合并 UAT、打包 UAT、跑测试；有成功的 UAT 包才能进入待发布
待发布完成发布 · 已结束测试流水里合并 Release、打包 Release、验证；至少一条流水验证通过并合回 master 才能结束任务
开发超时——超过结束时间且任务还停在未开始 / 开发中（红色 pill）
测试超时——超过结束时间且任务已在已提测 / 测试中 / 待发布（橙色 pill）
已结束——任务发布完成；状态不可再推进，产物仍可下载

任务状态与流水解耦：任务状态由按钮改，流水状态记录代码走到哪一步。流水动作会校验任务状态——任务还没「开始开发」时「合并 QA」置灰并提示；没「开始测试」时「合并 UAT」置灰；没「进入待发布」时「合并 Release」置灰。

3.3 流水状态

流水状态怎么进来说明与可用动作

冲突待解决合并出现冲突停在当前阶段，弹出冲突通知与 git 命令；流水卡片只有「已解决冲突 · 合并」一个按钮

自测通过点自测通过流水停在「已通过」，等任务「提测」后再点「合并 UAT」；不点提测则该按钮置灰

3.4 合并阶段与目标分支

四段固定：QA → UAT → Release → master。目标分支由阶段锁定，分支名取自应用配置的 branches（例如出行 App 为 qa / uat / Release / master）。

阶段目标分支由谁操作
QAqa开发
UATuat测试
ReleaseRelease测试
mastermaster测试（验证通过后合回）

3.5 冲突处理

  • 冲突时流水停在当前阶段，弹出「代码合并冲突通知」：需求编号 + 标题、流水线名（<需求标题>--<项目标识>）、Git 项目地址、项目标识、冲突分支、目标分支，附 5 条 git 命令（每行带复制按钮）。
  • 冲突分支是任务里配的 Feature 分支，不叫「临时分支」。
  • 需要基于 Feature 分支创建临时分支，让开发自己解决冲突，命名规则：
temp/Conflict_<目标分支>_feature/<feature>_<yy.MMDD.HHmm.ss>
例：temp/Conflict_qa_feature/transfer-direct-filter_26.1119.0942.31
  • 开发在临时分支上解决并推送完成后，回到平台点「已解决冲突 · 合并」，系统把临时分支合入目标分支，Feature 分支不做改动。
  • 冲突态流水卡片只有「已解决冲突 · 合并」一个按钮，没有「重试合并」。

3.6 三处硬门禁

  1. 提测前必须有 QA 包并自测通过，包要对应当前最新一次 QA 合并。
  2. 合并 Release 前必须有成功的 UAT 包。
  3. 验收（合回 master）前必须有成功的 Release 包并验证通过。

4. 超时与结束规则

判定条件说明
开发超时已超过结束时间，且任务状态为未开始 / 开发中（还没提测）红色 pill；归开发侧，要开发补时间或赶进度
测试超时已超过结束时间，且任务状态为已提测 / 测试中 / 待发布橙色 pill；归测试侧，开发已交付，不归属开发拖延
已结束任务点了「完成发布 · 已结束」优先级最高，超时不覆盖；任务没有「冲突」态，冲突体现在流水里

超时按当前状态归属，展示上必须区分具体类型：

  • 看板「超时」列仍是一列，但卡片 pill 显示「开发超时」或「测试超时」；
  • 首页「超时」KPI 下方小字给出「开发超时 X · 测试超时 Y」；
  • 我的任务列表状态列同样区分两种超时；
  • 任务详情有「超时归属」一行，含超期天数与所处阶段。

4A. 工作流程：谁在哪一步做什么

一条需求从提出到结束固定走四步，角色分工不重叠：产品建需求 → 开发负责人拆任务并指定任务负责人、测试负责人只登记测试人员 → 任务负责人领任务开发 → 测试接住提测后的任务直到发布结束。测试不建任务，任务全部来自开发负责人。

角色在哪操作做什么权限边界
产品负责人需求管理 → 新建需求填需求，指定开发 / 测试 / 产品负责人首页「我的需求」只看得到自己是产品负责人的需求
开发负责人需求详情 →「+ 新建任务」拆任务，指定任务负责人与计划开始 / 结束时间只有该需求的开发负责人或管理员可建任务，其余角色按钮置灰；任务全部由开发创建
测试负责人需求详情 →「+ 测试人员」登记参与测试的测试人员（负责人默认在内）不建任务、不改任务；被登记的测试人员也进入该需求的可见范围
任务负责人（开发）首页 → 进行中 → 任务详情开始开发 → 流水合并 QA / 打包 / 自测 → 提测只看得到负责人是自己的任务
测试首页 → 进行中 → 任务详情开始测试 → 合并 UAT / 打包 / 测试 → 待发布 → 验证并合回 master → 已结束接住已提测 / 测试中 / 待发布的任务

角色的可见范围由「我是这个需求的哪个负责人」决定，不由角色统一决定；因此同一个测试可能同时是 A 需求的负责人、B 需求的测试人员，两条需求都会出现在他的「我的需求」里。

6. 角色、级别与权限

角色能看到的能操作的
开发 dev我的任务 + 自己的流水任务上：开始开发、提测；流水上：合并 QA、打包 QA、自测通过 / 拒绝
测试 qa全部任务的流水任务上：开始测试、进入待发布、完成发布；流水上：合并 UAT、打包 UAT、合并 Release、打包 Release、验证通过 / 不通过、合回 master
管理员 admin全部数据任意阶段动作，维护应用配置、角色权限与人员
产品 pm需求与任务进度只读：提需求、看进度，不操作代码与打包
  • 级别：开发 / 测试 / 产品三个角色都分 L1 初级、L2 中级、L3 高级（测试与产品同样有 L3），共 9 个角色级别；级别只决定菜单可见范围，具体可执行动作仍由角色决定。管理员不设级别，固定拥有全部菜单。
  • 级别决定能力档位而非职责：例如测试 L2 可做合并 UAT / 验证 / 合回 master，测试 L3 额外可触发打包与下载产物；产品 L1 / L2 偏提需求与看进度，产品 L3 可下载产物做验收。
  • 权限配置由配置文件驱动（原型里是页面末尾的 perm-config JSON 块，当前 5 组 28 项）：每项含 key / label / menu / hash，menu=true 的项同时控制左侧菜单，其余为操作类权限（新建流水、合并、打包、验证等）。新增权限只改配置或在「角色权限」页导入 JSON，授权矩阵自动多一行。
  • 授权矩阵按「权限为行、角色 × 级别为列」，列头支持全选 / 清空；管理员列为只读全选。
  • 「角色权限」「人员管理」只有管理员可见；非管理员访问未授权地址显示无权限提示。

6A. 组件管理

组件（module）是应用依赖的代码库，不产出安装包；组件与应用是多对多关系，一个应用可以依赖多个组件，一个组件也可以被多个应用复用。

  • 应用侧开关：应用配置新增「组件」勾选框，默认关闭。勾选后表示该应用是组件应用，产物类型、产物扫描目录、渠道三项隐藏（组件不打包安装包），保存后该应用不再作为可打包应用出现在流水/构建里。
  • 组件管理页：左侧菜单新增「组件管理」，受菜单权限控制。页面顶部下拉选择应用（只列出未勾选组件的应用），下方列表展示该应用依赖的组件：组件名称、应用标识、仓库地址、版本号、添加时间，行尾可移除。
  • 新增组件：页头右侧「新增组件」按钮打开弹窗；先选择应用（未勾选组件的应用），再从组件列表中勾选一个或多个组件应用（已添加的置灰），保存后写入组件映射表。
  • 版本来源：添加组件时读取组件应用仓库的版本文件（优先 pubspec.yaml 的 version，其次 package.json 的 version），读不到时记为 —；版本用于组件列表展示与版本接口返回。
  • 版本接口说明：组件管理页右上角提供「获取版本接口」按钮，点击弹窗展示调用方式：构建脚本可用应用标识拉取组件与版本 GET /api/components?appCode={应用标识}，返回 { appCode, appName, components: [{ name, code, repo, version }] }；组件合并代码并推送仓库后，可调用 POST /api/components/version（body appCode / componentCode / version）更新版本号，返回 { appCode, appName, componentCode, componentName, version, component: { id, name, code, repo, platform, isComponent } }，包含组件的项目地址等应用信息。

6B. 操作日志

对服务端关键操作留痕，记录「谁在什么时间做了什么」，便于追溯配置变更与业务操作。

  • 记录范围：新增、更新、删除类操作都记录；查询（GET）与登录 / 登出等鉴权接口不记录。覆盖应用配置、组件管理、需求、任务、CI 流水、构建打包、人员管理、角色权限。
  • 记录内容：操作人（姓名、账号、角色快照）、动作（新增 / 更新 / 删除）、模块、可读描述（如「更新应用「出行 App」」）、请求方法与路径、响应状态码、脱敏后的请求参数、操作时间。请求体中的密码、token 等敏感字段写入前替换为 ***。
  • 实现方式：服务端全局拦截器统一采集，只处理 POST / PUT / PATCH / DELETE，按路由映射模块与动作；日志写入失败不影响主流程。公开接口（如组件版本上报）没有登录用户时，操作人记为「未登录调用」。
  • 日志页：左侧菜单新增「操作日志」，受菜单权限 logs 控制（管理员默认可见，其他角色在「角色权限」中授权）。页面支持按动作、模块、关键字（操作人 / 内容）筛选，表格展示时间、操作人、动作、模块、操作内容与结果，行可展开查看请求参数，底部分页。

7. 接口草案

GET/api/me当前账号与角色

GET/api/artifacts产物 / 构建列表（含打包中与失败），支持 status / appId / triggeredBy / start / end；下载直链不鉴权

GET/api/builds/:id单次构建详情（状态、进度、失败原因、产物）

GET/POST/PUT/api/staff人员列表 / 新增（账号 + 初始密码 + 角色 + 级别）/ 编辑（仅管理员）

GET/api/logs/modules日志中出现过的模块选项；需 logs 权限

8. 已确认规则

  1. 提测、合并 Release、验收都要先打包成功：提测要 QA 包且自测通过，合并 Release 要 UAT 包，验收要 Release 包；包必须对应最新一次该阶段合并。
  2. 不通过就回到上一节点：自测拒绝 / 测试不通过退回「已合入 QA」，Release 验证不通过退回「测试中」，都要重打包再流转。
  3. 验证通过后由测试点「合回 master」：release 直接合入 master，不额外走 MR；合入完成后流水结束，不提供重新打包。
  4. 合并无需排队，打包必须排队：打包机只有一份 clone，构建期间任何流水都禁止切分支合并；产物长期保留、下载不鉴权。
  5. 打包日志随时可查：流水卡片有「打包日志」按钮，正在打包与失败也能看；产物页除已入库外还列打包中（带进度）与失败（带原因），点行看构建详情与完整日志；运行中的流水禁止再次点打包。
  6. 流水不管任务开始，任务状态由任务按钮推进：流水只有合并 / 冲突待解决 / 已解决冲突 / 打包 QA·UAT·Release / 通过 / 拒绝；开始开发、提测、开始测试、进入待发布、完成发布都在任务详情上点。
  7. 打包前先填参数：点「打包 QA / UAT / Release」先弹窗填写版本号、Build 号并选择渠道；渠道选项来自应用配置（多个渠道用逗号分隔），版本号与 Build 号随构建入库并注入构建脚本环境变量。
  8. 组件的两种形态：应用勾选「组件」后只作为依赖被引用，不参与打包；组件管理页只为未勾选组件的应用维护组件列表，组件版本随映射保存并提供查询接口。
  9. 一个任务的提交记录只有一份：多条流水共用同一仓库与 Feature 分支，不分应用；任务详情「提交记录」显示该分支最近 20 条提交。
  10. 产物类型与构建脚本在应用里配置：应用按 Android / iOS 分开，流水只是选择应用 + 填 Feature 分支。
  11. 打包产物支持筛选：可按应用、触发人、构建时间范围（起止日期）查询，筛选项与状态筛选可叠加，筛选结果由服务端返回。
  12. 需求支持筛选：可按截止时间范围与负责人查询；负责人匹配开发 / 测试 / 产品负责人以及需求登记的测试人员，可与关键字、优先级叠加。

9. 原型操作路径

  1. 登录页选账号（陈默 开发 / 林晓 测试 / 王强 管理员 / 苏晴 产品 / 周然 开发）。
  2. 首页「我的任务」三个 tab（进行中 / 其他状态 / 我的需求）→ 行尾「任务详情」进入右侧抽屉。
  3. 任务详情：状态推进按钮 + tabs（概览 / CI 流水 / 提交记录 / 构建记录）。
  4. CI 流水卡片：合并 QA → 打包 → 自测通过 →（任务提测）→ 合并 UAT → 打包 → 合并 Release → 打包 → 验证通过 → 合回 master。
  5. 打包产物页：已入库 / 打包中 / 失败三态，点行看构建详情与打包日志；有产物时行尾提供「二维码」按钮，点击在按钮旁弹出下载直链二维码，移动端扫码即可下载产物。
  6. 应用配置勾选「组件」后，产物类型 / 产物扫描目录 / 渠道自动隐藏；组件管理页选择应用 → 查看组件与版本 → 新增组件弹窗勾选组件应用。

原型是本地模拟：数据存在 localStorage，不接真实 Git 与构建脚本，冲突与日志为演示数据。
